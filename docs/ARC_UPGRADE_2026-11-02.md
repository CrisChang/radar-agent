## 聚焦后的产品

**让 agent 在付费 API 调用中保留预算、付款与结果记录，在中断后恢复同一笔请求，并解释重试、延迟和费用。**

- 核心用户：接入付费 API 的 agent 开发者与服务提供者。
- 核心场景：服务端接受付款后，响应丢失；调用方重启后取得原结果。
- 交付入口：一个 TypeScript SDK/参考命令，后续再提供薄 MCP 适配层。
- Arc/Circle 的作用：USDC 付费、Gateway 归属与批次结算；不能只在介绍里提到 Arc。
- 服务商必须支持原授权幂等与结果恢复。未知能力先停止，不能承诺任意 x402 服务都可自动恢复。
- 预算目前是本机软件约束，不是链上受限钱包权限。私钥本身的权限不会因 CLI 预算而缩小。

## 基线与新增工作

基线：`9ddd10bf1edf7168d5afc9b7196643256dafca50`，原 `codex/arc-microgrants` 分支。
研发分支：`codex/arc-recovery`。Walrus 方向保持独立，不混入本轮 Arc 功能。

已有证据保持原口径：1,000 笔付款、0.232600 USDC、本次核查的 32 个共享批次；它们是同一控制人的两个钱包之间的功能验证，并非独立客户营收。新 SDK 的版本和验收记录须单独建立，不能用历史主网通过数覆盖新增代码。

本次初始交付：

1. `npm run demo:recovery`：无需钱包、凭据或联网。直接调用现有 `agentCall` 与磁盘账单写入代码。
2. 模拟服务端保存收款和结果后，强制退出首个子进程；它没有机会写入完成的 attempt 或捕获异常。
3. 新进程读取磁盘原记录、复用完全相同的授权取得结果；第三个进程只读取已存结果。
4. 自动核对一个模拟签名、一次预算预留、两个带付款授权的模拟请求、一次模拟计费、结果摘要一致。
5. 修复 `recovered` 标记：原实现依赖已完成 attempt 的数量，进程提前退出时会把恢复误标为首次调用。改为根据调用开始时是否存在原账单判断；未改变付款金额或重新签名策略。

演示的明确边界：真实的是客户端逻辑、文件持久化和进程重启；签名、服务商及收款均为模拟。它不访问生产 API，不连接 Gateway/RPC，不验证真实密码学签名或链上结算，也不证明第三方服务商具备幂等性。对机器断电、磁盘损坏和多进程同时写入仍需专门测试。
